Workflow File Explained to Automate Paper Search and Update

Below is a step-by-step blog article explaining the GitHub Actions workflow file update.yml in a clear, technical, and reader-friendly manner. It is written to fit naturally into the larger awesome-topics blog series and assumes the reader has basic familiarity with GitHub and CI pipelines.

The awesome-topics repository relies on a carefully designed GitHub Actions workflow to automate the entire research curation and publishing pipeline. This workflow is responsible for running scheduled updates, regenerating topic-wise pages, producing analytics, and deploying changes to GitHub Pages — without manual intervention.

This article walks through the workflow file step by step, explaining what each section does and why it exists.

Workflow Overview

At a high level, the workflow performs the following tasks:

  1. Triggers automatically (scheduled or event-based)
  2. Sets up a Python environment
  3. Runs content generation scripts
  4. Updates GitHub Pages content
  5. Generates statistics and visualizations
  6. Commits changes only if updates exist

The result is a self-maintaining research website.

Workflow Header and Triggers

name: paper-update

This assigns a human-readable name to the workflow. It will appear as “paper-update” in the GitHub Actions UI.

Trigger Conditions

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
  schedule:
    - cron: '0 0 * * *'

The workflow can be triggered in four ways:

  • Push to main
    Ensures updates run whenever new changes are merged.
  • Pull requests
    Allows validation of changes before merging.
  • Manual trigger (workflow_dispatch)
    Enables on-demand execution from the GitHub UI.
  • Scheduled run (cron)
    Executes daily at 00:00 UTC, ensuring the paper lists stay current even without repository activity.

This combination provides both reactive and proactive automation.

Permissions

permissions: write-all

The workflow requires write permissions to:

  • Commit generated files
  • Push updates to the repository
  • Deploy content to GitHub Pages

Without this, the automation would be read-only.

Job Definition

jobs:
  build:
    runs-on: ubuntu-latest

The workflow defines a single job named build, which runs on the latest Ubuntu runner provided by GitHub.

Environment Variables

env:
  TZ: "Asia/Kolkata"
  RUN_ENV: "prod"
  GH_USER: ${{ github.repository_owner }}
  PYTHONDONTWRITEBYTECODE: 1

These environment variables control runtime behaviour:

  • TZ – Ensures timestamps match the intended timezone
  • RUN_ENV – Allows switching between prod and dev logic
  • GH_USER – Dynamically sets the GitHub username
  • PYTHONDONTWRITEBYTECODE – Prevents .pyc files from polluting commits

This keeps the workflow deterministic and clean.

Step 1: Repository Checkout

- name: Checkout
  uses: actions/checkout@v2
  with:
    ref: ${{ github.head_ref }}
    fetch-depth: 0

This step:

  • Checks out the repository code
  • Fetches the full git history (required for committing changes)
  • Works correctly for both push and pull request events

Step 2: Python Environment Setup

- name: Set up Python 3.8
  uses: actions/setup-python@v2
  with:
    python-version: 3.8

The pipeline standardizes execution by:

  • Pinning Python to version 3.8
  • Ensuring compatibility with all scripts

Step 3: Install Dependencies

- name: Install dependencies
  run: |
    python -m pip install --upgrade pip
    if [ -f requirements.txt ]; then python -m pip install -r requirements.txt; fi

This step:

  • Upgrades pip
  • Installs dependencies only if requirements.txt exists

This makes the workflow robust to dependency changes.

Step 5: Creating GitHub Issues for Newly Detected Papers

The part of the workflow enables automatic GitHub issue creation whenever new research papers are detected. Although currently disabled, this section is important because it demonstrates how the pipeline can be extended from static page generation to active notifications.

This mechanism is designed to work in tandem with the DBLP watcher.

Step 5.1: Capturing the Detected Paper Summary

- name: Setup var
  id: vars
  run: |
    raw="${MSG:-}"
    {
      echo "raw<<EOF"
      echo "$raw"
      echo "EOF"
    } >> "$GITHUB_OUTPUT"

What This Step Does

This step captures the content of an environment variable called MSG and exposes it as a workflow output named raw.

  • MSG is expected to contain a Markdown-formatted summary of newly detected papers
  • The summary is typically generated by the DBLP watcher script in src/
  • If no new papers are found, MSG is empty or undefined

Why This Is Necessary

GitHub Actions outputs:

  • Cannot reliably handle multiline strings using simple echo
  • Require a special here-document (<<EOF) format for multiline values

This block ensures:

  • Newlines are preserved correctly
  • Markdown formatting remains intact
  • The output can be safely consumed by later steps

Key Line Explained

raw="${MSG:-}"

This assigns:

  • The value of MSG if it exists
  • An empty string if it does not

This prevents runtime errors.

Step 5.2: Conditional Issue Creation

- name: Create an issue for new papers
  if: ${{ steps.vars.outputs.raw != '' }}
  uses: JasonEtco/create-an-issue@v2
  env:
    MSG: ${{ steps.vars.outputs.raw }}
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  with:
    filename: .github/issue-template.md

What This Step Does

This step creates a GitHub issue automatically, but only if new papers were found. The condition:

if: ${{ steps.vars.outputs.raw != '' }}

ensures that:

  • An issue is created only when there is meaningful content
  • Empty or duplicate issues are avoided

How the Issue Is Created

The action JasonEtco/create-an-issue@v2:

  • Reads a predefined issue template
  • Substitutes environment variables into the template
  • Opens a new GitHub issue in the repository

Role of the Issue Template

with:
  filename: .github/issue-template.md

This file defines:

  • The issue title
  • Labels (e.g., papers, automation, dblp)
  • The Markdown structure of the issue body

Authentication and Permissions

env:
  GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  • GitHub automatically provides this token
  • It allows the workflow to create issues securely
  • No personal access token is required

Why This Section Is Commented Out in the Current Code Version

Currently, the number of topics and venues included takes more than the permissible limit of 360 minutes of execution in GitHub Actions. Hence, I personally run Step 4 on my laptop, comment out the code for Step 5, and then push the changes, which enables execution of Step 6 onwards.

When Should You Enable This?

Enable this section if the number of topics is less, and the workflow execution can be completed within the time limit of 360 minutes.

Alternative Solution (if you don’t want to execute Step 4 yourself)

Use a self-hosted runner on a local server or GCP, or AWS.

Step 6: Update README from YAML Data

- name: Update readme
  run: |
    cd scripts && python main.py merge_md_yaml

This step:

  • Reads structured YAML data from _data/
  • Merges it into README.md
  • Ensures the README always reflects the latest paper lists

The README acts as the canonical content source.

Step 7: Sync README to GitHub Pages

- name: Copy README.md to docs/index.md
  run: |
    mkdir -p docs
    cp README.md docs/index.md

This ensures:

  • docs/index.md mirrors the updated README.md
  • GitHub Pages renders the homepage correctly

No manual edits are ever made to docs/.

However, the user can make manual edits to README.md which will reflect in docs/index.md to enhance the presentation.

Step 8: Topic Statistics Generation

- name: Count papers per topic
  run: |
    cd scripts
    python count_topics.py

This script:

  • Counts papers per topic
  • Produces structured summary data
  • Enables analytics and visualizations

Step 9: Visualization Generation

- name: Generate topic distribution bar chart
  run: |
    cd scripts
    python generate_topic_barchart.py

This step:

  • Converts topic counts into a bar chart
  • Adds a visual overview of research coverage
  • Automatically updates figures used on the site

Step 10: Timestamp Generation

- name: Get date time
  id: date
  run: echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$GITHUB_OUTPUT"

This step:

  • Captures the exact UTC timestamp
  • Makes it available to later steps
  • Ensures commit messages are traceable and reproducible

Step 11: Automatic Commit and Push

- name: Commit Updated
  uses: stefanzweifel/git-auto-commit-action@v4
  with:
    commit_message: "auto update @ ${{ steps.date.outputs.date }} ${{ env.TZ }}"

This action:

  • Detects whether any files have changed
  • Commits updates only if necessary
  • Pushes changes to the repository

This prevents empty commits and keeps history clean.

Why This Workflow Design Works Well

  • Fully automated: No human intervention required
  • Idempotent: Safe to run daily
  • Traceable: Every update is version-controlled
  • Modular: Easy to extend with new steps
  • Research-friendly: Prioritizes reproducibility and clarity

Final Takeaway

This GitHub Actions workflow is the backbone of awesome-topics. It transforms a static repository into a living research platform, automatically curating, rendering, and publishing topic-wise paper lists on GitHub Pages.

By combining scheduled execution, structured data handling, and deterministic rendering, the workflow ensures that the site remains accurate, current, and maintenance-free.
