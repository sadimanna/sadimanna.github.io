In the previous article, we built a self-hosted GitHub Actions runner on GCP Always Free and used it to automate a real research pipeline (awesome-topics). That setup already works reliably—but it deliberately runs jobs directly on the host VM.

In this article, we take the next, critical step:

We introduce Docker-based isolation so that each workflow job runs inside a disposable container, even though the runner itself is persistent.

This is where a self-hosted runner starts behaving like a production-grade CI system, not just a long-running script executor.

Why Docker Isolation Is Necessary on Self-Hosted Runners

The Fundamental Problem

A self-hosted runner is:

  • Persistent

  • Stateful

  • Reused across jobs

  • Not automatically reset

Without Docker isolation, every job:

  • Shares the same Python installation

  • Shares the same filesystem

  • Shares caches and temporary files

  • Can affect future jobs in subtle ways

This is manageable at small scale — but fragile over time.

Typical Failure Modes Without Isolation

On a long-running VM, you eventually encounter:

  • Python dependency drift

  • Hidden state from previous runs

  • Disk growth from caches

  • Debugging sessions that “fix themselves” after cleanup

  • Hard-to-reproduce bugs

These problems do not exist on GitHub-hosted runners because those runners are ephemeral.

Docker isolation is how we re-introduce ephemerality on our own machine.

What “Docker-Based Isolation” Means (Precisely)

Docker isolation in GitHub Actions means:

The runner stays on the VM, but the job runs inside a container that is created at the start of the job and destroyed at the end.

Key properties:

  • Clean filesystem per job

  • Clean Python environment per job

  • No dependency leakage

  • Automatic cleanup

The VM runs only:

  • Docker daemon

  • GitHub runner service

Everything else happens inside containers.

Two Ways Docker Is Used in GitHub Actions

1. Job-Level Containers (Recommended)

jobs:
  update:
    runs-on: self-hosted
    container:
      image: python:3.10-slim
  • GitHub handles container lifecycle

  • Workspace is mounted automatically

  • Container is destroyed after the job

This is clean, declarative, and safe.

2. Manual docker run (Not Recommended)

docker run --rm python:3.10 python script.py

This gives control but adds complexity and error surface.

For your pipeline, job-level containers are the correct choice.

Step 1: Install Docker on the GCP Runner VM

SSH into the VM and run:

sudo apt update
sudo apt install -y docker.io

Enable Docker for the runner user:

sudo usermod -aG docker github
newgrp docker

Verify:

docker run hello-world

If this works, Docker is ready.

Step 2: Why We Do NOT Run the Runner Inside Docker

A common question is:

“Why not containerize the runner itself?”

Because:

  • The runner must manage jobs

  • The runner needs system-level access

  • Docker-inside-Docker adds complexity

  • GitHub does not recommend it for simple setups

Correct layering:

VM
 ├─ GitHub Runner (host)
 ├─ Docker daemon (host)
 └─ Job containers (ephemeral)

Step 3: Docker-Isolated Workflow for awesome-topics

Here is the Docker-isolated version of the same workflow from Article 1.

Key Differences from Article 1

  • Adds container: section

  • No Python installed on host is used

  • All dependencies live inside the container

  • Cleanup becomes simpler and safer

Full Workflow (Docker-Isolated)

name: Update Research Topics (Docker Isolated)
on:
  schedule:
    - cron: '0 1 * * *'
  workflow_dispatch:
concurrency:
  group: awesome-topics-runner
  cancel-in-progress: false
permissions:
  contents: write
  issues: write
jobs:
  update:
    runs-on: [self-hosted, gcp, awesome-topics]
    container:
      image: python:3.10-slim
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: pip install -r requirements.txt
      - name: Run DBLP crawler
        run: |
          cd src
          python main.py run --env=prod
      - name: Generate topic pages
        run: |
          cd scripts
          python generate_topics.py
      - name: Create issue for new papers
        if: ${{ steps.vars.outputs.raw != '' }}
        uses: JasonEtco/create-an-issue@v2
        env:
          MSG: ${{ steps.vars.outputs.raw }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          filename: .github/issue-template.md
      - name: Commit and push updates
        uses: stefanzweifel/git-auto-commit-action@v4
        with:
          commit_message: "Automated topic update"
          file_pattern: "_data _docs"

What Docker Isolation Changes (and What It Does Not)

What Changes

AspectBeforeAfterPython environmentHostContainerDependency pollutionPossibleImpossibleCleanup burdenHighLowerReproducibilityBest-effortStrong

What Does NOT Change

  • Runner registration

  • Firewall rules

  • GitHub tokens

  • Permissions

  • Triggers

  • Concurrency behavior

Docker affects execution, not authorization.

Do We Still Need Cleanup?

Yes — but less aggressively.

Why?

  • Container filesystem is destroyed automatically

  • Only the mounted workspace persists

You still want:

rm -rf $GITHUB_WORKSPACE/*

But you can usually drop:

pip cache purge
rm -rf ~/.cache/*

because:

  • Those caches live inside the container

  • The container disappears after the job

Performance Considerations on Free Tier

Constraints

  • 1 GB RAM

  • Shared CPU

  • No swap

  • Slow disk

Best Practices

  • Use python:*-slim

  • Avoid large base images

  • Avoid parallelism

  • Keep dependency list minimal

Docker adds a small startup cost, but the stability gain far outweighs it.

Security Improvements with Docker Isolation

Docker isolation gives you:

  • Process isolation

  • Filesystem isolation

  • Automatic cleanup

  • Reduced blast radius

However, it does not make PRs safe.

You must still avoid:

on: pull_request

on self-hosted runners.

Docker is defense in depth, not a permission system.

Why This Matters for Research Automation

For awesome-topics, Docker isolation guarantees:

  • Identical results across runs

  • No environment drift

  • No “it worked yesterday” bugs

  • Long-term reliability on a free VM

This is exactly what you want for:

  • Paper trackers

  • Dataset curation

  • Knowledge graphs

  • Automated surveys

When Docker Isolation Is Enough (and When It Is Not)

Docker Is Enough When

  • Workflows are scheduled

  • Code is trusted

  • Outputs are deterministic

  • Runner is private

Docker Is NOT Enough When

  • You want PR-based CI

  • You want untrusted code execution

  • You need multiple pipelines sharing one runner
