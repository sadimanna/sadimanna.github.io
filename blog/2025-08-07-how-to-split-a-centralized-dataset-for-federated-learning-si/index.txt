<p><img src="/images/blog/how-to-split-a-centralized-dataset-for-federated-learning-si/img1.jpeg" alt=""></p>
<p>Federated Learning (FL) holds the promise of training powerful AI models on decentralized data, preserving privacy and respecting data sovereignty. But before you can deploy a complex FL system, you need to test, simulate, and validate it. And that often starts with a classic challenge: you have one large, centralized dataset, and you need to pretend it lives in multiple, separate “silos” or “client” locations.</p>
<p>Manually dragging and dropping thousands of files is not an option. It’s tedious, error-prone, and not repeatable. What you need is a robust, scriptable way to partition your data.</p>
<p>In this guide, we’ll tackle a common scenario: splitting a large medical imaging dataset from a single source folder into multiple destination folders, each representing a different “hospital” or “client” in our federated network.</p>
<h3 id="the-scenario"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-scenario"><span class="anchor-icon">#</span></a>The Scenario</h3>
<p>Imagine we have a (imaginary) master folder <code>ITKSNAP_DATA</code>, containing thousands of NIfTI files (<em><code>.nii.gz</code></em>). These files are grouped by patient ID, and we want to distribute them into different client folders for our simulation.</p>
<ul>
<li>Patients P00— P20 belong to <code>ITKSNAP_1</code> (Client 1)</li>
<li>Patients P21 — P38 belong to <code>ITKSNAP_2</code> (Client 2)</li>
<li>Patients P39 — P54 belong to <code>ITKSNAP_3</code> (Client 3)</li>
<li>Patients P55 — P70 belong to <code>ITKSNAP_4</code> (Client 4)</li>
<li>Patients P71 — P99 belong to <code>ITKSNAP_5</code> (Client 5)</li>
</ul>
<p>For each patient <code>PXX</code>, there are multiple associated files we need to move together, such as <em><code>****image\_PXX.nii.gz****</code></em>, <em><code>label\_PXX.nii.gz</code></em>, etc., or if the data contains multiple sequences like T1, T1CE, or T2, as in the BraTS dataset, the files will be named <code>BraTS20_Training_038_t1.nii.gz</code> , <code>BraTS20_Training_038_t2.nii.gz</code> , <code>BraTS20_Training_038_seg.nii.gz</code> .</p>
<p>Here are three programmatic approaches to solve this, ranging from a quick command-line solution to a robust and reusable Python script.</p>
<hr>
<h3 id="approach-1-the-data-driven-shellscript"><a class="heading-anchor" aria-hidden tabindex="-1" href="#approach-1-the-data-driven-shellscript"><span class="anchor-icon">#</span></a>Approach 1: The Data-Driven Shell Script</h3>
<p>This is a powerful and concise method for users comfortable in a Linux, macOS, or WSL terminal. We define our data distribution plan in arrays and let a single loop do all the work. It’s the epitome of the “Don’t Repeat Yourself” (DRY) principle.</p>
<p>Best for: Quick, configurable, one-off tasks in a Bash environment.</p>
<h4 id="the-code"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-code"><span class="anchor-icon">#</span></a>The Code</h4>
<pre><code class="hljs language-text">#!/bin/bash  
# --- Configuration --- 
# Define the start and end of each number range 
starts=(21 39 55 71) 
ends=(38 54 70 94)  
# Define the corresponding destination folder number for each range 
dest_nums=(1 2 3 4 5)  
# Define the source directory 
source_dir="ITKSNAP_DATA" 
# --- End of Configuration ---  
# Loop through the array indices (0, 1, 2, 3) 
for i in "${!starts[@]}"; do
   start=${starts[i]}
   end=${ends[i]}
   dest_num=${dest_nums[i]}
   dest_dir="ITKSNAP_${dest_num}"
   echo "--- Processing range ${start}-${end} -> ${dest_dir} ---" 
   # Create the destination directory if it doesn't exist 
   mkdir -p "$dest_dir" 
   # Loop through the actual file numbers in the current range 
   for j in $(seq $start $end); do 
       # Check if the main file exists before trying to move anything
       if [ -f "${source_dir}/image_P${j}.nii.gz" ]; then 
           # Use brace expansion to move all related files at once
           mv "${source_dir}/"{image_P,label_P}"${j}.nii.gz" "$dest_dir/"
           echo "Moved files for P${j}"
       fi
   done 
done  
echo "--- All operations complete. ---"
</code></pre>
<h4 id="how-itworks"><a class="heading-anchor" aria-hidden tabindex="-1" href="#how-itworks"><span class="anchor-icon">#</span></a>How It Works</h4>
<ul>
<li>Configuration Arrays: We store the start numbers, end numbers, and destination folder indices in separate arrays. This keeps the configuration clean and separate from the logic.</li>
<li>Master Loop: The <em><code>for i in “${!starts[@]}”</code></em> loop iterates through the <em>indices</em> of the arrays (0, 1, 2, 3), allowing us to access the corresponding elements from <em><code>starts</code></em>, <em><code>ends</code></em>, and <em><code>dest\_nums</code></em> in each iteration.</li>
<li><em><code>mkdir -p</code></em>: This command safely creates the destination directory, including any parent directories, and doesn’t complain if it already exists.</li>
<li>Brace Expansion: The line <em><code>mv “${source\_dir}/”{image\_P,…}”${j}.nii.gz”</code></em> is a shell superpower. It expands to run the <em><code>mv</code></em> command on all four filenames in a single, clean line.</li>
</ul>
<hr>
<h3 id="approach-2-the-shell-script-with-afunction"><a class="heading-anchor" aria-hidden tabindex="-1" href="#approach-2-the-shell-script-with-afunction"><span class="anchor-icon">#</span></a>Approach 2: The Shell Script with a Function</h3>
<p>If you find the array logic a bit dense, wrapping the core operation in a function can improve readability. You define the “what” in the function and then simply call it with the “how” and “where.”</p>
<p>Best for: Shell scripters who prefer a more procedural and explicitly readable style.</p>
<h4 id="the-code-1"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-code-1"><span class="anchor-icon">#</span></a>The Code</h4>
<p>We do this example for the BraTS dataset, which has a file name of the format <code>BraTS20_training_007_seg.nii.gz</code>, that is, the patient indices have leading zeros in the file name.</p>
<pre><code class="hljs language-text">#!/bin/bash  
# Define a function to move a range of files 
move_file_range() {
   local start=$1
   local end=$2
   local dest_num=$3
   local padding_width=$4 # Accept padding as an argument
   local source_dir="BraTS2020"
   local dest_dir="BraTS2020_${dest_num}"
   echo "--- Processing range ${start}-${end} -> ${dest_dir} ---"
   mkdir -p "$dest_dir" 
   for i in $(seq $start $end); do 
       # Format the number 'i' with leading zeros for BraTS
       local padded_i=$(printf "%0*d" $padding_width $i)

       if [ -f "${source_dir}/BraTS20_training_${padded_i}_seg.nii.gz" ]; then 
           mv "${source_dir}/BraTS20_training_${padded_i}_"{t1,t1ce,t2,flair,seg}".nii.gz" "$dest_dir/"
           echo "Moved files for P${i}"
       fi   
    done 
}  
# Now, just call the function for each task 
move_file_range 0 43 1 3
move_file_range 44 65 2 3
move_file_range 66 67 3 3
move_file_range 68 86 4 3
move_file_range 87 88 5 3
echo "--- All operations complete. ---"
</code></pre>
<h4 id="how-itworks-1"><a class="heading-anchor" aria-hidden tabindex="-1" href="#how-itworks-1"><span class="anchor-icon">#</span></a>How It Works</h4>
<ul>
<li><strong><code>move_file_range()</code></strong>: We encapsulate the entire logic for moving one batch of files into a reusable function.</li>
<li><strong>Parameters (<code>$1</code>, <code>$2</code>, <code>$3</code>, <code>$4</code>)</strong>: The function accepts the start number, end number, destination index, and padding width as arguments. If the file names do not have leading zeros, the fourth argument can be removed.</li>
<li>Clear Calls: The main part of the script is now a simple, readable list of function calls that clearly state the intent for each data split.</li>
</ul>
<hr>
<h3 id="approach-3-the-robust-python-script-recommended"><a class="heading-anchor" aria-hidden tabindex="-1" href="#approach-3-the-robust-python-script-recommended"><span class="anchor-icon">#</span></a>Approach 3: The Robust Python Script (Recommended)</h3>
<p>For data management, especially in a research or production pipeline, Python is the undisputed champion. It’s more verbose than a shell script but offers unparalleled safety, readability, and cross-platform portability (it works on Windows, macOS, and Linux without changes).</p>
<p>Best for: Repeatable, maintainable, and safe data management workflows.</p>
<h4 id="the-code-2"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-code-2"><span class="anchor-icon">#</span></a>The Code</h4>
<p>Save this as <em><code>organize\_data.py</code></em> and run it with <em><code>python organize\_data.py</code></em>.</p>

<h4 id="how-itworks-2"><a class="heading-anchor" aria-hidden tabindex="-1" href="#how-itworks-2"><span class="anchor-icon">#</span></a>How It Works</h4>
<ul>
<li>Clear Configuration: All settings are at the top, making the script easy to adapt for new datasets or splitting strategies.</li>
<li><em><code>os.path.join</code></em>: This function intelligently creates file paths that work on any operating system, avoiding common errors with slashes (<em><code>/</code></em>) vs. backslashes (<em><code>\</code></em>).</li>
<li><em><code>os.makedirs(…, exist\_ok=True)</code></em>: The Python equivalent of <em><code>mkdir -p</code></em>, ensuring our script doesn’t fail if the destination folder already exists.</li>
<li>Safety and Explicitness: The code explicitly checks if each file exists before attempting to move it, preventing crashes. The recommendation to use <em><code>shutil.copy</code></em> for a dry run before switching to the destructive <em><code>shutil.move</code></em> is a critical best practice.</li>
</ul>
<h3 id="conclusion-which-should-youchoose"><a class="heading-anchor" aria-hidden tabindex="-1" href="#conclusion-which-should-youchoose"><span class="anchor-icon">#</span></a>Conclusion: Which Should You Choose?</h3>
<p>While shell scripts are fantastic for quick, personal tasks, the Python script is the clear winner for any serious, repeatable workflow. Its explicitness, safety features, and cross-platform nature make it the ideal choice for preparing data in a collaborative or long-term research project.</p>
<p>Properly partitioning your data is the first crucial step in building a meaningful federated learning simulation. By automating this process, you ensure it’s fast, accurate, and ready for the next stage of your experiment. Now that your data is properly siloed, you’re one step closer to training your first federated model.</p>
