<h3 id="project-objective"><a class="heading-anchor" aria-hidden tabindex="-1" href="#project-objective"><span class="anchor-icon">#</span></a>Project Objective</h3>
<p>The goal of <em>awesome-topics</em> is to:</p>
<ul>
<li>Automatically discover newly published research papers</li>
<li>Organize them by <strong>topic → venue → year</strong></li>
<li>Store results in a structured, version-controlled format</li>
<li>Generate clean, navigable Markdown pages</li>
<li>Publish updates automatically via GitHub Pages</li>
</ul>
<p>Once configured, the repository continuously maintains a public research index at:</p>
<pre><code class="hljs language-text">https://&#x3C;user-name>.github.io/awesome-topics
</code></pre>
<hr>
<p>The code for this article can be found here:</p>
<p><a href="https://github.com/sadimanna/awesome-topics" title="https://github.com/sadimanna/awesome-topics"><strong>GitHub - sadimanna/awesome-topics: Comprehensive and timely academic papers on federated learning…</strong><br>
*Comprehensive and timely academic papers on federated learning, machine unlearning and other related topics. - GitHub …*github.com</a></p>
<p>Read the rest of the article to understand how the code works, and create your own list of research papers.</p>
<hr>
<h3 id="high-level-pipelineoverview"><a class="heading-anchor" aria-hidden tabindex="-1" href="#high-level-pipelineoverview"><span class="anchor-icon">#</span></a>High-Level Pipeline Overview</h3>
<p>The project follows a clear, multi-stage pipeline:</p>
<ol>
<li><strong>Topic configuration</strong> defines <em>what</em> to search for</li>
<li><strong>DBLP querying logic</strong> discovers new papers</li>
<li><strong>Structured YAML storage</strong> persists paper metadata</li>
<li><strong>Markdown generation scripts</strong> create topic pages</li>
<li><strong>GitHub Actions</strong> runs the pipeline and deploys updates</li>
</ol>
<p>Each stage is cleanly separated, which makes the system robust, extensible, and easy to debug.</p>
<p><img src="/images/blog/awesome-topics-fully-automated-research-paper-curation-on-gi/img2.png" alt=""></p>
<p>Data Flow Diagram</p>

<pre><code class="hljs language-text">awesome-topics/
│
</code></pre>
<p>Each directory plays a specific role in the automation pipeline.</p>
<p><img src="/images/blog/awesome-topics-fully-automated-research-paper-curation-on-gi/img3.png" alt=""></p>
<p>System Architecture Diagram</p>
<hr>
<h3 id="1-topic-configuration-_configs"><a class="heading-anchor" aria-hidden tabindex="-1" href="#1-topic-configuration-_configs"><span class="anchor-icon">#</span></a>1. Topic Configuration (<code>_configs/</code>)</h3>
<p>The <code>_configs/</code> directory defines <strong>what research topics are tracked</strong> and <strong>how papers are searched</strong>.</p>
<p>Each configuration file specifies:</p>
<ul>
<li>Topic identifier (slug)</li>
<li>Search keywords</li>
<li>Venue filters (e.g., NeurIPS, ICML, ICLR, CVPR, IJCAI)</li>
<li>DBLP query parameters</li>
</ul>
<h3 id="design-rationale"><a class="heading-anchor" aria-hidden tabindex="-1" href="#design-rationale"><span class="anchor-icon">#</span></a>Design Rationale</h3>
<p>This configuration-driven design allows:</p>
<ul>
<li>Adding new topics without modifying the source code</li>
<li>Independent control over search behaviour per topic</li>
<li>Easy scaling to dozens of research areas</li>
</ul>
<p>In practice, adding a new topic simply requires creating a new configuration file.</p>
<hr>
<h3 id="2-paper-discovery-via-dblpsrc"><a class="heading-anchor" aria-hidden tabindex="-1" href="#2-paper-discovery-via-dblpsrc"><span class="anchor-icon">#</span></a>2. Paper Discovery via DBLP (<code>src/</code>)</h3>
<p>The <code>src/</code> directory contains all logic related to <strong>searching DBLP and collecting paper metadata</strong>.</p>
<h3 id="responsibilities"><a class="heading-anchor" aria-hidden tabindex="-1" href="#responsibilities"><span class="anchor-icon">#</span></a>Responsibilities</h3>
<ul>
<li>Construct DBLP queries using <code>_configs/</code></li>
<li>Fetch publication data via DBLP APIs</li>
<li>Parse and normalize responses</li>
<li>Detect newly added papers</li>
<li>Avoid duplicates across runs</li>
</ul>
<p>The output of this stage is <strong>structured paper metadata</strong>, not Markdown.</p>
<hr>
<h3 id="3-structured-paper-storage_data"><a class="heading-anchor" aria-hidden tabindex="-1" href="#3-structured-paper-storage_data"><span class="anchor-icon">#</span></a>3. Structured Paper Storage (<code>_data/</code>)</h3>
<p>All discovered papers are stored in <strong>YAML files</strong> inside the <code>_data/</code> directory.</p>
<p>Each YAML file corresponds to a topic and contains:</p>
<ul>
<li>Topic metadata</li>
<li>Venue-wise paper lists</li>
<li>Year-wise grouping</li>
<li>Stable markers for incremental updates</li>
</ul>
<h3 id="why-yaml"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-yaml"><span class="anchor-icon">#</span></a>Why YAML?</h3>
<p>Using YAML as an intermediate representation provides:</p>
<ul>
<li>Clear separation between data and presentation</li>
<li>Deterministic, idempotent updates</li>
<li>Easy version control and inspection</li>
<li>Reusability for future analytics or visualization</li>
</ul>
<p>This layer acts as the <strong>single source of truth</strong> for the project.</p>
<hr>
<h3 id="4-markdown-page-generation-scripts"><a class="heading-anchor" aria-hidden tabindex="-1" href="#4-markdown-page-generation-scripts"><span class="anchor-icon">#</span></a>4. Markdown Page Generation (<code>scripts/</code>)</h3>
<p>The <code>scripts/</code> directory is responsible for <strong>transforming structured YAML data into Markdown pages</strong>.</p>
<h3 id="key-responsibilities"><a class="heading-anchor" aria-hidden tabindex="-1" href="#key-responsibilities"><span class="anchor-icon">#</span></a>Key Responsibilities</h3>
<ul>
<li>Read topic-wise YAML files from <code>_data/</code></li>
<li>Generate Markdown files for each topic</li>
<li>Create collapsible sections for venues and years</li>
<li>Insert anchors and table-of-contents links</li>
<li>Ensure consistent formatting across topics</li>
</ul>
<h4 id="importantly"><a class="heading-anchor" aria-hidden tabindex="-1" href="#importantly"><span class="anchor-icon">#</span></a>Importantly:</h4>
<blockquote>
<p><em><strong>The Markdown files in</strong></em> <code>docs/</code> <em><strong>are not edited directly.</strong></em> <em>They are</em> <em><strong>fully generated and updated by scripts</strong></em> <em>based on the YAML data.</em></p>
</blockquote>
<p>This ensures that presentation logic is fully automated and reproducible.</p>
<hr>
<h3 id="5-github-pages-contentdocs"><a class="heading-anchor" aria-hidden tabindex="-1" href="#5-github-pages-contentdocs"><span class="anchor-icon">#</span></a>5. GitHub Pages Content (<code>docs/</code>)</h3>
<p>The <code>docs/</code> directory contains the <strong>rendered output</strong> that GitHub Pages serves.</p>
<h3 id="docs_topics"><a class="heading-anchor" aria-hidden tabindex="-1" href="#docs_topics"><span class="anchor-icon">#</span></a><code>docs/_topics/</code></h3>
<ul>
<li>Contains topic-wise Markdown pages</li>
<li>Each page is generated from YAML via scripts</li>
<li>URLs map cleanly to topic names</li>
</ul>
<h3 id="docsindexmd"><a class="heading-anchor" aria-hidden tabindex="-1" href="#docsindexmd"><span class="anchor-icon">#</span></a><code>docs/index.md</code></h3>
<ul>
<li>Acts as the landing page</li>
<li>Automatically updated to include new topics</li>
<li>Links to all topic-wise pages</li>
<li>Lastly, it is to be noted that the <em><strong>index.md</strong></em> file is generated from the <strong>README.md</strong> file, and the user can edit it manually to include any extra information the user wants to display. For example, I have listed the conference venues and journal names from which I have searched the listed papers.</li>
</ul>
<p>GitHub Pages renders this directory directly, making the site live after every successful automation run.</p>
<hr>
<h3 id="6-full-automation-with-githubactions"><a class="heading-anchor" aria-hidden tabindex="-1" href="#6-full-automation-with-githubactions"><span class="anchor-icon">#</span></a>6. Full Automation with GitHub Actions</h3>
<p>The pipeline is orchestrated using <strong>GitHub Actions</strong> defined in <code>.github/workflows/</code>.</p>
<h3 id="workflow-execution"><a class="heading-anchor" aria-hidden tabindex="-1" href="#workflow-execution"><span class="anchor-icon">#</span></a>Workflow Execution</h3>
<p>On a scheduled trigger or manual dispatch:</p>
<ol>
<li>The repository is checked out</li>
<li>DBLP search scripts in <code>src/</code> are executed</li>
<li>YAML files in <code>_data/</code> are updated if new papers are found</li>
<li>Markdown generation scripts in <code>scripts/</code> regenerate topic pages</li>
<li>Changes are committed only if updates exist</li>
<li>GitHub Pages redeploys automatically</li>
</ol>
<p>This results in a <strong>self-updating research website</strong>.</p>
<p><img src="/images/blog/awesome-topics-fully-automated-research-paper-curation-on-gi/img4.png" alt=""></p>
<p>Conceptual Functional Call Level Diagram (May not exactly match the function calls)</p>
<hr>
<h3 id="incremental-updates-and-deduplication"><a class="heading-anchor" aria-hidden tabindex="-1" href="#incremental-updates-and-deduplication"><span class="anchor-icon">#</span></a>Incremental Updates and Deduplication</h3>
<p>To ensure stability across runs:</p>
<ul>
<li>Previously recorded papers are never duplicated</li>
<li>New papers are appended in the correct venue/year section</li>
<li>Existing anchors and page structure remain unchanged</li>
</ul>
<p>This makes the system safe to run daily.</p>
<hr>
<h3 id="design-philosophy"><a class="heading-anchor" aria-hidden tabindex="-1" href="#design-philosophy"><span class="anchor-icon">#</span></a>Design Philosophy</h3>
<p>The project follows a few key principles:</p>
<ul>
<li><strong>Data first</strong>: YAML is the authoritative layer</li>
<li><strong>Code-driven presentation</strong>: Markdown is generated, never edited</li>
<li><strong>Configuration over hardcoding</strong></li>
<li><strong>Reproducibility and transparency</strong></li>
</ul>
<p>This architecture mirrors best practices used in large-scale data pipelines.</p>
<hr>
<h3 id="who-is-thisfor"><a class="heading-anchor" aria-hidden tabindex="-1" href="#who-is-thisfor"><span class="anchor-icon">#</span></a>Who Is This For?</h3>
<ul>
<li>Researchers maintaining public paper lists</li>
<li>Labs curating structured reading resources</li>
<li>Survey authors tracking literature growth</li>
<li>Students organizing research topics systematically</li>
</ul>
<p>The system scales naturally as research interests expand.</p>

<h3 id="closing-remarks"><a class="heading-anchor" aria-hidden tabindex="-1" href="#closing-remarks"><span class="anchor-icon">#</span></a>Closing Remarks</h3>
<p><em>awesome-topics</em> turns research paper curation into a <strong>fully automated, reproducible pipeline</strong> by cleanly separating configuration, data collection, storage, and presentation. Once set up, it requires no maintenance — yet continuously reflects the evolving research landscape.</p>
<p>By combining DBLP queries, structured YAML storage, script-driven Markdown generation, and GitHub Actions automation, the project demonstrates a practical and scalable approach to research curation.</p>
