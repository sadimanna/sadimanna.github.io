<p>This article directly matches the below intended design idea:</p>
<blockquote>
<p>run part of the workflow on a self-hosted runner, commit results, and let that push trigger the rest of the workflow on GitHub-hosted runners.</p>
</blockquote>
<p>This is particularly useful if the GCP VM that we created in the previous part of our article series has usage limitations. Check the article below for some context:</p>
<p><a href="https://medium.com/the-owl/awesome-topics-fully-automated-research-paper-curation-on-github-pages-part-4-709ea8b515d3" title="https://medium.com/the-owl/awesome-topics-fully-automated-research-paper-curation-on-github-pages-part-4-709ea8b515d3"><strong>awesome-topics: Fully Automated Research Paper Curation on GitHub Pages — Part 4</strong><br>
<em>A Deep, Practical Guide to a self-hosted runner on GCP/AWS to run a GitHub workflow file</em>medium.com</a></p>
<hr>
<p>In the previous article of this series, we used a self-hosted GitHub Actions runner on GCP. However, there is still one architectural problem left to solve:</p>
<blockquote>
<p><em><strong>Not every workflow step should run on a self-hosted runner.</strong></em></p>
</blockquote>
<p>In this article, we design a <strong>hybrid GitHub Actions pipeline</strong> where:</p>
<ul>
<li><strong>Phase 1</strong> runs on a <strong>self-hosted runner</strong></li>
<li><strong>Phase 2</strong> runs on <strong>GitHub-hosted runners</strong></li>
<li>The two phases are connected explicitly using a <code>workflow_run</code> trigger. The transition between phases is handled explicitly, avoiding fragile push-based chaining.</li>
</ul>
<p>This pattern is the <strong>correct, scalable, and future-proof design</strong> for serious automation pipelines like <code>awesome-topics</code>.</p>
<hr>
<h3 id="why-a-hybrid-pipeline-is-necessary"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-a-hybrid-pipeline-is-necessary"><span class="anchor-icon">#</span></a>Why a Hybrid Pipeline Is Necessary</h3>
<h4 id="the-problem-with-everything-on-self-hosted"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-problem-with-everything-on-self-hosted"><span class="anchor-icon">#</span></a>The Problem with “Everything on Self-Hosted”</h4>
<p>A self-hosted runner is still:</p>
<ul>
<li>Persistent</li>
<li>Privileged</li>
<li>Network-reachable</li>
<li>Able to mutate the repository</li>
</ul>
<p>Running <strong>all</strong> workflows there creates risk:</p>
<ul>
<li>PRs become dangerous</li>
<li>Permissions are harder to reason about</li>
<li>Failures affect unrelated pipelines</li>
<li>Free-tier resources are wasted on builds</li>
<li>Prevents overusage of GCP VM instances.</li>
</ul>
<h4 id="the-problem-with-everything-on-github-hosted"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-problem-with-everything-on-github-hosted"><span class="anchor-icon">#</span></a>The Problem with “Everything on GitHub-Hosted”</h4>
<p>Conversely, GitHub-hosted runners are:</p>
<ul>
<li>Ephemeral</li>
<li>Stateless</li>
<li>Rate-limited</li>
<li>Paid beyond free quotas</li>
</ul>
<p>They are poorly suited for:</p>
<ul>
<li>Long-running crawlers</li>
<li>External API polling (DBLP)</li>
<li>Stateful data regeneration</li>
<li>Research automation</li>
</ul>
<hr>
<h3 id="the-hybridsolution"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-hybridsolution"><span class="anchor-icon">#</span></a>The Hybrid Solution</h3>
<blockquote>
<p>Split responsibilities cleanly.</p>
</blockquote>
<h3 id="phase-1producer"><a class="heading-anchor" aria-hidden tabindex="-1" href="#phase-1producer"><span class="anchor-icon">#</span></a>Phase 1 — Producer</h3>
<ul>
<li>Runs on a <strong>self-hosted runner</strong></li>
<li>Scheduled / manual</li>
<li>Generates data</li>
<li>Commits and pushes</li>
</ul>
<h3 id="phase-2consumer"><a class="heading-anchor" aria-hidden tabindex="-1" href="#phase-2consumer"><span class="anchor-icon">#</span></a>Phase 2 — Consumer</h3>
<ul>
<li>Runs on <strong>GitHub-hosted runners</strong></li>
<li>Triggered by <code>push</code></li>
<li>Builds, deploys, publishes</li>
<li>Never mutates repository state</li>
</ul>
<hr>
<h3 id="high-level-architecture"><a class="heading-anchor" aria-hidden tabindex="-1" href="#high-level-architecture"><span class="anchor-icon">#</span></a>High-Level Architecture</h3>
<p>Conceptually:</p>
<pre><code class="hljs language-text">(schedule / manual)
        ↓
</code></pre>
<p>Each phase has <strong>clear ownership</strong> and <strong>clear trust boundaries</strong>.</p>
<hr>
<h3 id="workflow-1-producer-self-hosted"><a class="heading-anchor" aria-hidden tabindex="-1" href="#workflow-1-producer-self-hosted"><span class="anchor-icon">#</span></a>Workflow 1: Producer (Self-Hosted)</h3>
<p>This workflow is responsible for <strong>generating and updating content</strong>.</p>
<h4 id="key-properties"><a class="heading-anchor" aria-hidden tabindex="-1" href="#key-properties"><span class="anchor-icon">#</span></a>Key Properties</h4>
<ul>
<li>No PR triggers</li>
<li>No <code>push</code> trigger</li>
<li>Commits only deterministic outputs</li>
<li>Runs on GCP Always Free</li>
</ul>
<h4 id="workflow-1-search-dblp-fullyaml"><a class="heading-anchor" aria-hidden tabindex="-1" href="#workflow-1-search-dblp-fullyaml"><span class="anchor-icon">#</span></a>Workflow 1 (search-dblp): Full YAML</h4>
<pre><code class="hljs language-text">name: search-dblp

on:
  workflow_dispatch:
  schedule:
    - cron: '0 0 * * 0'  # every sunday at 00:00 hrs UTC
    
permissions:
  contents: write
  issues: write

concurrency:
  group: awesome-topics-runner
  cancel-in-progress: false

jobs:
  search:
    runs-on: self-hosted
    timeout-minutes: 7200
    env:
      TZ: "Asia/Kolkata"
      RUN_ENV: "prod" # within ['prod', 'dev']
      GH_USER: ${{ github.repository_owner }}
      PYTHONDONTWRITEBYTECODE: 1

    outputs:
      data_changed: ${{steps.diff.outputs.data_changed }}

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          # ref: ${{ github.head_ref }}
          fetch-depth: 0

      ################################################################################
      # install dependencies
      ################################################################################

      - name: Install dependencies
        run: |
          python3 -m pip install --upgrade pip
          if [ -f requirements.txt ]; then python3 -m pip install -r requirements.txt; fi

      # ============================================
      # Run DBLP Watcher to get latest papers
      # ============================================
      - name: Run dblp watcher
        run: |
          cd src
          python3 main.py run --env=${{ env.RUN_ENV }}

      - name: Setup var
        id: vars
        run: |
          raw="${MSG:-}"
          {
            echo "raw&#x3C;&#x3C;EOF"
            echo "$raw"
            echo "EOF"
          } >> "$GITHUB_OUTPUT"

      ################################################################################
      # CREATES ISSUE FOR NEW PAPERS
      ################################################################################
      - name: Create an issue for new papers
        if: ${{ steps.vars.outputs.raw != '' }}
        uses: JasonEtco/create-an-issue@v2
        env:
          MSG: ${{ steps.vars.outputs.raw }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          filename: .github/issue-template.md

      ################################################################################
      # COMMIT CHANGES IF ANY
      ################################################################################
      # ------------------------------------------------
      # Detect whether _data/*.yaml changed
      # ------------------------------------------------
      - name: Detect data changes
        id: diff
        run: |
          git status --porcelain
          if git diff --name-only | grep -q '^_data/.*\.ya\?ml$'; then
            echo "data_changed=true" >> "$GITHUB_OUTPUT"
          else
            echo "data_changed=false" >> "$GITHUB_OUTPUT"
          fi

      - name: Get date time
        id: date
        run: echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$GITHUB_OUTPUT"

      # ------------------------------------------------
      # Commit only if changes exist
      # ------------------------------------------------
      - name: Commit Updated
        if: steps.diff.outputs.data_changed == 'true'
        uses: stefanzweifel/git-auto-commit-action@v4
        with:
          commit_message: "new papers added @ ${{ steps.date.outputs.date }} ${{ env.TZ }}"

      - name: Cleanup
        run: |
          rm -rf $GITHUB_WORKSPACE/*
</code></pre>
<h4 id="why-this-workflow-does-not-triggeritself"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-this-workflow-does-not-triggeritself"><span class="anchor-icon">#</span></a>Why This Workflow Does NOT Trigger Itself</h4>
<p>Even though it pushes commits:</p>
<ul>
<li>It is <strong>not triggered by</strong> <code>push</code></li>
<li>It runs only on <code>schedule</code> or <code>workflow_dispatch</code></li>
<li>Looping is architecturally impossible</li>
</ul>
<p>This is <strong>stronger than relying on idempotency alone</strong>.</p>
<hr>
<h3 id="workflow-2-consumer-github-hosted"><a class="heading-anchor" aria-hidden tabindex="-1" href="#workflow-2-consumer-github-hosted"><span class="anchor-icon">#</span></a>Workflow 2: Consumer (GitHub-Hosted)</h3>
<p>This workflow reacts to changes produced by Workflow 1.</p>
<h4 id="responsibilities"><a class="heading-anchor" aria-hidden tabindex="-1" href="#responsibilities"><span class="anchor-icon">#</span></a>Responsibilities</h4>
<ul>
<li>Update <strong>README.md</strong> and <strong>docs/index.md</strong></li>
<li>Build the site</li>
<li>Run checks</li>
<li>Deploy GitHub Pages</li>
</ul>
<h4 id="workflow-2-update-paper-list-fullyaml"><a class="heading-anchor" aria-hidden tabindex="-1" href="#workflow-2-update-paper-list-fullyaml"><span class="anchor-icon">#</span></a>Workflow 2 (update-paper-list): Full YAML</h4>
<pre><code class="hljs language-text">name: update-paper-list

on:
  workflow_run:
    workflows: ["search-dblp"]
    types: [completed]
  workflow_dispatch:
    
permissions:
  contents: write
  issues: write

jobs:
  update:
    if: >
      github.event_name == 'workflow_dispatch' ||
      ( github.event.workflow_run.conclusion == 'success' &#x26;&#x26;
      contains(github.event.workflow_run.head_commit.message, 'new papers added') )

    runs-on: ubuntu-latest
    timeout-minutes: 3600
    env:
      TZ: "Asia/Kolkata"
      RUN_ENV: "prod" # within ['prod', 'dev']
      GH_USER: ${{ github.repository_owner }}
      PYTHONDONTWRITEBYTECODE: 1

    steps:
      - name: Checkout
        uses: actions/checkout@v2
        with:
          # ref: ${{ github.head_ref }}
          fetch-depth: 0

      - name: Set up Python 3.8
        uses: actions/setup-python@v2
        with:
          python-version: 3.8

      - name: Install dependencies
        run: |
          python3 -m pip install --upgrade pip
          if [ -f requirements.txt ]; then python3 -m pip install -r requirements.txt; fi


      - name: Update readme
        run: |
          cd scripts &#x26;&#x26; python3 main.py merge_md_yaml

      - name: Copy README.md to docs/index.md

      - name: Count papers per topic
        run: |
          cd scripts
          python3 count_topics.py

      - name: Generate topic distribution bar chart
        run: |
          cd scripts
          python3 generate_topic_barchart.py
      ################################################################################
      # COMMIT CHANGES IF ANY
      ################################################################################
      - name: Get date time
        id: date
        run: echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$GITHUB_OUTPUT"

<blockquote>
<p><strong>Update: Why the push-based workflow failed and how it was fixed</strong></p>
</blockquote>
<blockquote>
<p>In the original setup, I tried to chain workflows using a simple <code>push</code> trigger: one workflow would update the repository, and another would react to that push. On paper, this looks reasonable—but it turns out GitHub intentionally blocks this pattern when the push is made by a workflow using <code>GITHUB_TOKEN</code>. Even though files were updated and GitHub Pages rebuilt correctly, the downstream workflow never ran, because GitHub suppresses workflow triggers caused by automation-authored commits to prevent infinite loops.</p>
</blockquote>
<hr>
<blockquote>
<p><strong>Update: Workflow orchestration improvements</strong></p>
</blockquote>
<blockquote>
<p>The automation pipeline was refactored to use <code>workflow_run</code><strong>–based chaining</strong> instead of push-triggered workflows, ensuring deterministic execution and eliminating recursive triggers caused by <code>GITHUB_TOKEN</code> commits. The DBLP ingestion workflow now explicitly detects whether <code>_data/*.yaml</code> files actually changed using a Git diff, and exports this signal as a workflow output. The downstream rendering workflow runs <strong>only when real data changes occur</strong>, preventing no-op commits, unnecessary Pages rebuilds, and CI noise. Together, these changes add loop protection, path-level guards, and cleaner separation between data ingestion and documentation generation.</p>
</blockquote>
<h3 id="why-this-separation-is-so-important"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-this-separation-is-so-important"><span class="anchor-icon">#</span></a>Why This Separation Is So Important</h3>
<h4 id="security"><a class="heading-anchor" aria-hidden tabindex="-1" href="#security"><span class="anchor-icon">#</span></a>Security</h4>
<ul>
<li>Self-hosted runner never executes PR code</li>
<li>GitHub-hosted runners handle public events</li>
<li>No secrets exposed to forks</li>
</ul>
<h4 id="reliability"><a class="heading-anchor" aria-hidden tabindex="-1" href="#reliability"><span class="anchor-icon">#</span></a>Reliability</h4>
<ul>
<li>Generator failures do not block deployments</li>
<li>Builds do not consume free-tier VM resources</li>
<li>Each phase can be debugged independently</li>
</ul>
<h4 id="scalability"><a class="heading-anchor" aria-hidden tabindex="-1" href="#scalability"><span class="anchor-icon">#</span></a>Scalability</h4>
<ul>
<li>You can add more generators</li>
<li>You can parallelize consumers</li>
<li>You can move generators to other clouds later</li>
</ul>
