<p><img src="/images/blog/awesome-topics-fully-automated-research-paper-curation-on-gi/img1.jpeg" alt=""></p>
<p>GitHub Actions are excellent for CI/CD, but many <strong>research automation workflows</strong> do not fit the standard CI mold. Pipelines that crawl external sources, regenerate datasets, update markdown indexes, and commit results back to the repository benefit from <strong>persistent, controlled execution environments</strong>. Also, there is a time limit of 360 minutes for execution on GitHub-hosted runners.</p>
<p>In this article, we build a <strong>self-hosted GitHub Actions runner on Google Cloud Platform (GCP)</strong> using the “<strong>Always Free” tier</strong>, and adapt it to our research automation project: <code>awesome-topics</code>.</p>
<p>This post is deliberately long and detailed. It answers not only <em>how</em> to set things up, but <em>why each decision is made</em>, addressing common confusions and subtle pitfalls along the way.</p>
<blockquote>
<p><em><strong>Scope of this article</strong></em></p>
</blockquote>
<ul>
<li>No Docker (yet)</li>
<li>No PR-based CI</li>
<li>Focus on scheduled, trusted automation</li>
<li>Zero-cost, production-safe setup</li>
</ul>
<p><strong>Docker isolation</strong> and <strong>hybrid workflows</strong> are covered in later articles.</p>
<hr>
<h3 id="why-a-self-hosted-runner"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-a-self-hosted-runner"><span class="anchor-icon">#</span></a>Why a Self-Hosted Runner?</h3>
<p>The <code>awesome-topics</code> pipeline performs tasks that are:</p>
<ul>
<li>Scheduled (daily DBLP queries)</li>
<li>Stateful (updates <code>_data/</code> and <code>_docs/</code>)</li>
<li>Deterministic (same inputs → same outputs)</li>
<li>Repository-mutating (commits and pushes)</li>
<li>Not performance-intensive</li>
</ul>
<p><a href="https://medium.com/the-owl/awesome-topics-fully-automated-research-paper-curation-on-github-pages-part-1-4098f4222d66" title="https://medium.com/the-owl/awesome-topics-fully-automated-research-paper-curation-on-github-pages-part-1-4098f4222d66"><strong>awesome-topics: Fully Automated Research Paper Curation on GitHub Pages — Part 1</strong><br>
<em>Get the venue and year-wise research paper list at <user-name>.github.io/awesome-topics</em>medium.com</a></p>
<p>Running these repeatedly on GitHub-hosted runners is unnecessary and brittle. A <strong>self-hosted runner</strong> gives us:</p>
<ul>
<li>Persistent environment</li>
<li>Full control over dependencies</li>
<li>No GitHub minutes consumed</li>
<li>Predictable scheduling</li>
</ul>
<blockquote>
<p>However, the primary reason for switching to the idea of a self-hosted runner is the time limit of 360 minutes time limit in GitHub Actions as the default maximum runtime for any single job.</p>
</blockquote>
<hr>

<pre><code class="hljs language-text">GitHub Scheduler / Manual Trigger
            ↓
</code></pre>
<p><strong>Important:</strong><br>
GitHub never connects <em>to</em> your VM.<br>
The runner <strong>polls GitHub outbound</strong> over HTTPS.</p>

<h3 id="step-3-firewallrules"><a class="heading-anchor" aria-hidden tabindex="-1" href="#step-3-firewallrules"><span class="anchor-icon">#</span></a>Step 3: Firewall Rules</h3>
<h3 id="in-gcp"><a class="heading-anchor" aria-hidden tabindex="-1" href="#in-gcp"><span class="anchor-icon">#</span></a>In GCP:</h3>
<ul>
<li>Firewall rules are <strong>network-level objects</strong></li>
<li>They are evaluated dynamically</li>
<li>Adding or removing rules does <strong>not require VM recreation</strong></li>
</ul>
<h3 id="security-principle"><a class="heading-anchor" aria-hidden tabindex="-1" href="#security-principle"><span class="anchor-icon">#</span></a>Security Principle</h3>
<p>A self-hosted runner:</p>
<ul>
<li><strong>Does not need inbound web traffic</strong></li>
<li><strong>Does not receive jobs from GitHub</strong></li>
<li><strong>Only makes outbound connections</strong></li>
</ul>
<p>Therefore:</p>
<blockquote>
<p><em>The firewall should allow</em> <em><strong>SSH only</strong></em> <em>and block everything else by default.</em></p>
</blockquote>
<h3 id="minimal-firewallpolicy"><a class="heading-anchor" aria-hidden tabindex="-1" href="#minimal-firewallpolicy"><span class="anchor-icon">#</span></a>Minimal Firewall Policy</h3>
<p>Your runner needs:</p>
<ul>
<li><strong>Inbound:</strong> SSH (port 22) from <em>you</em></li>
<li><strong>Outbound:</strong> unrestricted (default)</li>
</ul>
<p>No HTTP, HTTPS, or custom ports are required.</p>
<p>Below is a <strong>precise, step-by-step guide to setting up firewall rules for a GCP VM used as a self-hosted GitHub Actions runner</strong>, with explanations tailored to your <code>awesome-topics</code> <strong>automation pipeline</strong>.</p>
<p>This focuses on <strong>minimum required access</strong> and <strong>free-tier safety</strong>.</p>

<h3 id="common-mistakes-toavoid"><a class="heading-anchor" aria-hidden tabindex="-1" href="#common-mistakes-toavoid"><span class="anchor-icon">#</span></a>Common Mistakes to Avoid</h3>
<ul>
<li>Opening SSH to <code>0.0.0.0/0</code></li>
<li>Using default “allow all” rules</li>
<li>Running runner as root</li>
<li>Allowing PR workflows</li>
</ul>
<h3 id="why-do-i-need-my-publicip"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-do-i-need-my-publicip"><span class="anchor-icon">#</span></a>“Why do I need my public IP?”</h3>
<p>A firewall rule must specify <strong>who is allowed to SSH</strong>.</p>
<p>If you write:</p>
<pre><code class="hljs language-text">0.0.0.0/0
</code></pre>
<p>You are saying:</p>
<blockquote>
<p><em>“Anyone on the internet may attempt to log in.”</em></p>
</blockquote>
<p>Restricting SSH to:</p>
<pre><code class="hljs language-text">YOUR_PUBLIC_IP/32
</code></pre>
<p>reduces the attack surface to effectively zero.</p>
<hr>
<h3 id="ipv6-confusion-commonpitfall"><a class="heading-anchor" aria-hidden tabindex="-1" href="#ipv6-confusion-commonpitfall"><span class="anchor-icon">#</span></a>IPv6 Confusion (Common Pitfall)</h3>
<p>If you use IPv6 and see:</p>
<blockquote>
<p>Invalid IPv6 address or range. Enter the lowest IPv6 address in the subnet.</p>
</blockquote>
<p>This means your CIDR prefix is invalid.</p>
<p><strong>Rule:</strong><br>
For a single IPv6 address, always use <code>/128</code>.</p>
<p>Example:</p>
<pre><code class="hljs language-text">2401:db00:abcd:1234:5678:9abc:def0:1111/128
</code></pre>
<p>This is correct, unambiguous, and secure.</p>

<h3 id="step-9-the-workflow-and-why-it-looks-thisway"><a class="heading-anchor" aria-hidden tabindex="-1" href="#step-9-the-workflow-and-why-it-looks-thisway"><span class="anchor-icon">#</span></a>Step 9: The Workflow (and Why It Looks This Way)</h3>
<p>Here is the complete workflow used by <code>awesome-topics</code>.</p>
<pre><code class="hljs language-text">name: auto

on:
  push:
    branches: ['main']
  workflow_dispatch:
  schedule:
    - cron: '0 0 * * *'
    
permissions:
  contents: write
  issues: write

concurrency:
  group: awesome-topics-runner
  cancel-in-progress: false

jobs:
  update:
    runs-on: self-hosted
    env:
      TZ: "Asia/Kolkata"
      RUN_ENV: "prod" # within ['prod', 'dev']
      GH_USER: ${{ github.repository_owner }}
      PYTHONDONTWRITEBYTECODE: 1

    steps:
      - name: Checkout
        uses: actions/checkout@v2
        with:
          ref: ${{ github.head_ref }}
          fetch-depth: 0

      - name: Install dependencies
        run: |
          python3 -m pip install --upgrade pip
          if [ -f requirements.txt ]; then python3 -m pip install -r requirements.txt; fi

      # ============================================
      # Run DBLP Watcher to get latest papers
      # ============================================
      - name: Run dblp watcher
        run: |
          cd src
          python3 main.py run --env=${{ env.RUN_ENV }}

      - name: Setup var
        id: vars
        run: |
          raw="${MSG:-}"
          {
            echo "raw&#x3C;&#x3C;EOF"
            echo "$raw"
            echo "EOF"
          } >> "$GITHUB_OUTPUT"

      - name: Create an issue for new papers
        if: ${{ steps.vars.outputs.raw != '' }}
        uses: JasonEtco/create-an-issue@v2
        env:
          MSG: ${{ steps.vars.outputs.raw }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          filename: .github/issue-template.md

      - name: Update readme
        run: |
          cd scripts &#x26;&#x26; python3 main.py merge_md_yaml

      - name: Copy README.md to docs/index.md
        run: |
          mkdir -p docs
          cp README.md docs/index.md

      - name: Count papers per topic
        run: |
          cd scripts
          python3 count_topics.py

      - name: Generate topic distribution bar chart
        run: |
          cd scripts
          python3 generate_topic_barchart.py
      ################################################################################
      # COMMIT CHANGES IF ANY
      ################################################################################
      - name: Get date time
        id: date
        run: echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$GITHUB_OUTPUT"

      - name: Commit Updated
        uses: stefanzweifel/git-auto-commit-action@v4
        with:
          commit_message: "auto update @ ${{ steps.date.outputs.date }} ${{ env.TZ }}"

      - name: Cleanup
        run: |
          rm -rf $GITHUB_WORKSPACE/*
</code></pre>
<hr>
<h3 id="why-is-cleanup-required"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-is-cleanup-required"><span class="anchor-icon">#</span></a>Why is cleanup required?</h3>
<p>Deleting the GitHub workspace (<code>rm -rf $GITHUB_WORKSPACE/*</code>) is required on self-hosted runners because the workspace <strong>persists across runs</strong>. Without cleanup, leftover files from previous jobs can affect diffs, cause incorrect commits, introduce non-deterministic behaviour, and eventually exhaust disk space. Removing the workspace ensures <strong>each run starts from a clean checkout</strong>, matching the behaviour of GitHub-hosted (ephemeral) runners and keeping the automation reliable.</p>
<hr>
<h3 id="final-securitymodel"><a class="heading-anchor" aria-hidden tabindex="-1" href="#final-securitymodel"><span class="anchor-icon">#</span></a>Final Security Model</h3>
<ul>
<li>Forks cannot trigger the workflow</li>
<li>PRs are ignored</li>
<li>GitHub never SSHs into your VM</li>
<li>SSH is restricted to you</li>
<li>Runner polls GitHub outbound only</li>
</ul>
<p>This is <strong>safe by design</strong>.</p>
