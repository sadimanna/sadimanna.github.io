<p>Now, let’s assume you don’t have a powerful GPU.</p>
<p>Or perhaps you want to deploy MedGemma on:</p>
<ul>
<li>A laptop</li>
<li>An edge server</li>
<li>A CPU-only cloud machine</li>
</ul>
<p>In this case, using PyTorch may be inefficient.</p>
<p>This is where <strong>GGUF + llama-cpp</strong> shines.</p>
<h3 id="why-usegguf"><a class="heading-anchor" aria-hidden tabindex="-1" href="#why-usegguf"><span class="anchor-icon">#</span></a>Why Use GGUF?</h3>
<p>GGUF is a fully packaged, quantized model format designed specifically for inference.</p>
<p>Unlike HuggingFace models:</p>
<ul>
<li>It is not a training checkpoint</li>
<li>It is not meant for fine-tuning</li>
<li>It is optimized for runtime speed and portability</li>
</ul>
<p>It runs through <strong>llama.cpp</strong>, a C++ inference engine.</p>
<p>No PyTorch.<br>
No dynamic graph.<br>
No GPU required.</p>
<h3 id="step-1install-llama-cpp"><a class="heading-anchor" aria-hidden tabindex="-1" href="#step-1install-llama-cpp"><span class="anchor-icon">#</span></a>Step 1 — Install llama-cpp</h3>
<pre><code class="hljs language-bash">pip install llama-cpp-python
</code></pre>
<p>If you want optional GPU acceleration:</p>
<pre><code class="hljs language-text">CMAKE_ARGS="-DLLAMA_CUBLAS=on" pip install llama-cpp-python --no-cache-dir
</code></pre>
<p>This compiles CUDA kernels into the backend.</p>
<h3 id="step-2loading-a-ggufmodel"><a class="heading-anchor" aria-hidden tabindex="-1" href="#step-2loading-a-ggufmodel"><span class="anchor-icon">#</span></a>Step 2 — Loading a GGUF Model</h3>
<pre><code class="hljs language-python"><span class="hljs-keyword">from</span> llama_cpp <span class="hljs-keyword">import</span> Llama
model = Llama.from_pretrained(
    repo_id=<span class="hljs-string">"unsloth/medgemma-4b-it-GGUF"</span>,
    filename=<span class="hljs-string">"medgemma-4b-it-Q4_K_M.gguf"</span>,
    n_gpu_layers=-<span class="hljs-number">1</span>
)
</code></pre>
<p>Here’s what happens internally.</p>
<h3 id="what-is-from_pretrained-in-llama-cpp"><a class="heading-anchor" aria-hidden tabindex="-1" href="#what-is-from_pretrained-in-llama-cpp"><span class="anchor-icon">#</span></a>What is from_pretrained() In llama-cpp?</h3>
<p>It:</p>
<ol>
<li>Downloads the .gguf file</li>
<li>Memory-maps it (no full RAM duplication)</li>
<li>Initializes quantized matrix kernels</li>
<li>Allocates KV cache buffers</li>
</ol>
<p>Unlike PyTorch, this is static inference — no graph building.</p>
<p>However, if you load a multi-modal model in this way, you will only receive a text-only response, and the model will not be able to see your image input. The issue stems from a fundamental design choice in llama.cpp: <strong>It assumes everything is a Causal LLM by default.</strong></p>
<h3 id="the-causal-assumption"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-causal-assumption"><span class="anchor-icon">#</span></a><strong>The “Causal” Assumption</strong></h3>
<p>By default, llama.cpp treats every GGUF file as a <strong>Causal Language Model</strong>.</p>
<p>In simple terms, a Causal LLM is a “decoder-only” architecture designed to predict the next word in a sequence from left to right. This works perfectly for Llama 3 or Mistral, but it creates a “tunnel vision” problem:</p>
<ol>
<li><strong>Directionality:</strong> It only looks backward at previous tokens.</li>
<li><strong>Input Type:</strong> It expects a sequence of discrete integers (tokens), not a high-dimensional grid of pixels.</li>
</ol>
<p>When you try to run a multimodal model without specific instructions, llama.cpp ignores the vision component entirely because the standard inference loop doesn't know what a "pixel" is.</p>
<h3 id="the-solution-the-multi-modal-projector"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-solution-the-multi-modal-projector"><span class="anchor-icon">#</span></a><strong>The Solution: The Multi-Modal Projector</strong></h3>
<p>To fix this, we have to bridge the gap between “seeing” (Vision Encoder) and “thinking” (LLM). In the llama.cpp ecosystem, this is handled by a <strong>Projector</strong> (often called an mmproj file).</p>
<p>The projector is essentially a translator. It takes the output from a vision model (like CLIP) and turns it into “visual tokens” that the Causal LLM can understand as if they were just more words in the prompt.</p>
<p><strong>The Fix:</strong> You must explicitly load the projector alongside the model:</p>
<ul>
<li><strong>CLI:</strong> Use the --mmproj flag.</li>
<li><strong>Python:</strong> Use a ChatHandler (like Llava15ChatHandler) to link the two files.</li>
</ul>
<h3 id="revised-code-for-loading-ggufmodel"><a class="heading-anchor" aria-hidden tabindex="-1" href="#revised-code-for-loading-ggufmodel"><span class="anchor-icon">#</span></a>Revised Code for loading GGUF model</h3>
<pre><code class="hljs language-python"><span class="hljs-keyword">from</span> llama_cpp <span class="hljs-keyword">import</span> Llama

<h3 id="understanding-ggufvariants"><a class="heading-anchor" aria-hidden tabindex="-1" href="#understanding-ggufvariants"><span class="anchor-icon">#</span></a>Understanding GGUF Variants</h3>
<ul>
<li><strong>Q4_K_M</strong> → 4-bit grouped quantization</li>
<li><strong>Q8_0</strong> → 8-bit</li>
<li><strong>BF16</strong> → full precision</li>
</ul>
<p>These are pre-quantized. There is no runtime quantization happening. The compression was done offline.</p>
<h3 id="what-does-n_gpu_layers-do"><a class="heading-anchor" aria-hidden tabindex="-1" href="#what-does-n_gpu_layers-do"><span class="anchor-icon">#</span></a>What Does n_gpu_layers Do?</h3>
<p>This is crucial.</p>
<p>If:</p>
<pre><code class="hljs language-text">n_gpu_layers=0
</code></pre>
<p>All transformer layers run on CPU.</p>
<p>If:</p>
<pre><code class="hljs language-text">n_gpu_layers=10
</code></pre>
<p>The first 10 layers run on GPU.</p>
<p>If:</p>
<pre><code class="hljs language-text">n_gpu_layers=-1
</code></pre>
<p>All layers offload to GPU (if CUDA enabled).</p>
<p>Internally, <strong>llama.cpp</strong> splits the transformer stack and routes matrix multiplications accordingly.</p>
<p>This allows hybrid CPU/GPU execution — something Transformers does not easily expose.</p>
<h3 id="the-final-hurdle-feeding-theimage"><a class="heading-anchor" aria-hidden tabindex="-1" href="#the-final-hurdle-feeding-theimage"><span class="anchor-icon">#</span></a><strong>The Final Hurdle: “Feeding” the Image</strong></h3>
<p>Even with the projector loaded, many developers run into a second wall: <strong>the model still can’t see the image.</strong></p>
<p>This usually happens because of how images are passed in code. If you use PIL.Image.open() or a raw requests stream, you are holding a Python object. llama-cpp-python doesn't know what to do with that.</p>
<p><strong>The Solution:</strong> You must encode your image into a <strong>Base64 Data URI</strong>.</p>
<p>The model expects a string that looks like this:<br>
data:image/jpeg;base64,/9j/4AAQSkZJRg...</p>
<p>By converting your image bytes into this specific string format, the Python bindings can successfully pass the visual data to the mmproj projector, which then translates it for the LLM.</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">import</span> base64
<span class="hljs-keyword">import</span> requests
<span class="hljs-keyword">from</span> io <span class="hljs-keyword">import</span> BytesIO

<span class="hljs-comment"># 3. HELPER: Convert Image to Base64 (The "Format")</span>
<span class="hljs-keyword">def</span> <span class="hljs-title function_">get_image_data_uri</span>(<span class="hljs-params">image_source</span>):
    <span class="hljs-comment"># Works for both local paths and URLs</span>
    <span class="hljs-keyword">if</span> image_source.startswith(<span class="hljs-string">"http"</span>):
        <span class="hljs-comment"># The line you asked about: fetching the raw bytes from a URL</span>
        response = requests.get(image_source, headers={<span class="hljs-string">"User-Agent"</span>: <span class="hljs-string">"example"</span>})
        image_bytes = response.content
    <span class="hljs-keyword">else</span>:
        <span class="hljs-keyword">with</span> <span class="hljs-built_in">open</span>(image_source, <span class="hljs-string">"rb"</span>) <span class="hljs-keyword">as</span> f:
            image_bytes = f.read()
    
    base64_encoded = base64.b64encode(image_bytes).decode(<span class="hljs-string">'utf-8'</span>)
    <span class="hljs-keyword">return</span> <span class="hljs-string">f"data:image/jpeg;base64,<span class="hljs-subst">{base64_encoded}</span>"</span>

<span class="hljs-comment"># 4. EXECUTE: Multimodal Inference</span>
image_url = <span class="hljs-string">"https://example.com/path-to-medical-scan.jpg"</span> <span class="hljs-comment"># Replace with your image</span>

<p>Internally:</p>
<ul>
<li>The embedded chat template formats messages</li>
<li>Tokens are generated sequentially</li>
<li>Attention is computed using quantized matrix multiplication kernels</li>
<li>KV cache grows token by token</li>
</ul>
<p>Because everything is C++ and statically optimized, it performs very well on the CPU compared to PyTorch.</p>

<h3 id="when-should-you-usegguf"><a class="heading-anchor" aria-hidden tabindex="-1" href="#when-should-you-usegguf"><span class="anchor-icon">#</span></a>When Should You Use GGUF?</h3>
<p>Use GGUF if:</p>
<ul>
<li>You do not need fine-tuning</li>
<li>You want a portable single file</li>
<li>You are deploying to CPU environments</li>
<li>You want predictable inference behaviour</li>
</ul>
<p>It is not ideal for research iteration, but excellent for deployment.</p>
<h3 id="final-thoughts"><a class="heading-anchor" aria-hidden tabindex="-1" href="#final-thoughts"><span class="anchor-icon">#</span></a>Final Thoughts</h3>
<p>Both approaches solve different problems.</p>
<p>BitsAndBytes:</p>
<ul>
<li>Research flexibility</li>
<li>GPU speed</li>
<li>Fine-tuning compatibility</li>
</ul>
<p>GGUF:</p>
<ul>
<li>CPU efficiency</li>
<li>Lightweight deployment</li>
<li>Single-file portability</li>
</ul>
<p>The right choice depends on your goal, not just your hardware.</p>
